# STM32WBA 双终端 V2V 语音工程

## 1. 工程边界

本目录是独立的 STM32WBA54 双终端 V2V 试验工程。它不是仓库根目录下
`E04-2G4M10S1AX` 的 CH9140 方向灯固件。两个工程内部目录名相似，但角色、协议、
外设和 HEX 都不相同，禁止混烧。

| 工程 | 无线方式 | 风险输入 | 输出 |
|---|---|---|---|
| 根目录 `E04-2G4M10S1AX` | WBA Central 连接 MP257 外接 CH9140 Peripheral | MP257 的 `RISK LEFT/RIGHT/CENTER/CLEAR` | PA7/PA5 方向灯与 ACK |
| 本目录 `V2V_keil/E04-2G4M10S1AX` | 两个 WBA 终端直接广播并扫描 BLE Manufacturer Data | 两端位置、速度、航向、姿态和距离趋势 | 本地 MP3 方向语音 |

本工程没有使用 MP257 雷达数据，也没有通过 CH9140 转发 `RISK` 文本。它当前是
“固定一个对端的双车状态广播和本地语音实验”，不是标准 C-V2X 协议栈，也不能直接
替代量产级车联网安全协议。

## 2. 当前版本和构建入口

- MCU：STM32WBA54KGUx
- 源码版本：`v1.8.2`
- Keil Target：`02_test`
- Keil 工程：`MDK-ARM/02_test.uvprojx`
- CubeMX 文件：`02_test.ioc`
- 编译器配置：Arm Compiler 6 / ARMCLANG
- 输出：`MDK-ARM/02_test/02_test.axf`、`MDK-ARM/02_test.hex`
- 本端协议 ID：`0x1001`
- 唯一期望对端 ID：`0x1002`
- BLE 协议版本：2

当前工程源码是端点 A 配置。真正做两端互发时，端点 B 必须单独构建为本端
`0x1002`、期望对端`0x1001`。两块板不能直接烧同一个 HEX：若都广播`0x1001`且都只
过滤`0x1002`，双方不会处理对方数据。当前 ID 是`app_ble.c`内编译期宏，不是运行时
自动分配，也没有第二个 Keil Target 自动生成互补固件。

`02_test.ioc` 目前只完整登记了 USART1。USART2、PA1/PA2 复用选择脚及相关初始化是
源码中的人工扩展。以后若用 CubeMX 重新生成代码，必须检查 USER CODE 区和 Keil 文件组，
避免 USART2、路由器以及 GPS/IMU 源文件被删除或配置被覆盖。

## 4. 硬件接口和引脚

### 4.1 调试和外部状态串口 USART1

| 信号 | WBA 引脚 | 配置 |
|---|---|---|
| USART1_TX | PB12 | 115200，8N1，DMA TX |
| USART1_RX | PA8 | 115200，8N1，DMA Receive-to-Idle |

USART1 有两种用途：

1. 输出启动、BLE、风险和语音调试日志；
2. 可选接收外部控制器提供的协议 v2 状态帧，临时覆盖本机传感器状态后进行广播。

当前二进制调试帧回传宏默认关闭，所以平时主要观察 ASCII 日志。

### 4.2 复用串口 USART2

| 信号 | WBA 引脚 | 配置 |
|---|---|---|
| USART2_TX | PA12 | GPS/IMU 115200；播放语音时临时改为 9600 |
| USART2_RX | PB8 | 单字节中断接收 |

USART2 经外部 TTL 多路选择板连接三个模块。选择信号定义为 `B:A = PA2:PA1`：

| PA2(B) | PA1(A) | 通道 | 波特率 |
|---:|---:|---|---:|
| 0 | 0 | GPS | 115200 |
| 0 | 1 | IMU | 115200 |
| 1 | 0 | MP3 语音模块 | 9600 |

PA1/PA2 是普通推挽输出，默认低电平，即上电进入 GPS 通道。语音播放期间会停止 USART2
接收、清除串口错误、切换通道和波特率；播放命令发送后恢复原通道并重新启动接收。

### 4.3 调试下载口

CubeMX 保留标准 SWD：PA13 为 SWDIO，PA14 为 SWCLK。烧录时还应连接 GND、目标板
参考电压和按需要连接 NRST。

## 5. 从上电到主循环

启动顺序如下：

```text
HAL_Init
  → MX_APPE_Config（无线时钟预配置）
  → SystemClock_Config / PeriphCommonClock_Config
  → GPIO、GPDMA1、ICACHE、RAMCFG、RNG、RTC
  → USART1、USART2
  → TTL_UART2_Router_Init
      ├── 初始化 GNSS 解析器
      ├── 初始化 IMU 解析器
      └── 默认选择 GPS 通道
  → 打印 V2X Node v1.8.2 和编译时间
  → MX_APPE_Init
      ├── BLE Host、GAP/GATT、生成服务初始化
      ├── 启动非连接广播
      └── 启动主动扫描
  → 启动 USART1 DMA 和 USART2 单字节中断接收
  → 主循环
```

主循环不使用 RTOS 线程，而是协作式反复执行：

```text
MX_APPE_Process()
  → 处理 USART1 已收数据并调用 APP_BLE_UartRxData()
  → APP_BLE_Protocol_Tick()
      ├── 每 1 s 更新广播状态
      └── 检查对端 2 s 超时
  → TTL_UART2_Router_Process()
      ├── 取一条待播语音并发送 MP3 命令
      └── 处理 GNSS/IMU 已就绪数据
```

语音通道切换包含 50 ms 级 `HAL_Delay`，因此播放时主循环会短时阻塞。它适合当前单条
提示实验，但若后续需要严格实时采样，应改成非阻塞子状态机。

### 5.1 为什么上电没有播放问候语

`main.c`会调用`TTL_UART2_PlayStartupGreeting()`，但源码默认把
`TTL_UART2_STARTUP_SONG_NUMBER`定义为`0`。`0`表示关闭，函数会立即返回，所以当前
固件上电不播放语音是预期行为，不代表UART2或MP3模块故障。

此前原版把启动曲目设为1，而曲目1已经定义为“左侧来车”。这会让每次复位都产生一次
假的风险提示，因此不能恢复为1。若语音卡中新增了独立问候文件，应先确定其
真实曲目号`N`，确保不与风险曲目1～5重叠，再在Keil Target的C/C++预处理宏中增加：

```text
TTL_UART2_STARTUP_SONG_NUMBER=N
```

重新Rebuild和烧录后，启动函数会等待CX-SP5F模块500 ms、切到VOICE通道、以9600
波特率依次发送“停止→单曲播放完停止→指定曲目”，然后恢复传感器通道。没有专用
问候曲目前应保持默认`0`。

## 6. GPS、IMU 与 UART2 时分调度

### 6.1 GNSS

GPS 解析器只接收 NMEA-0183 RMC 语句：

- 从 `$` 开始缓存，到 CR/LF 结束；
- 验证 NMEA XOR 校验和和 RMC 类型；
- 要求状态字段为 `A`；
- 字段 3～6 转换为带符号经纬度，内部单位为 `1e-7` 度；
- 字段 7 节转换为 `cm/s`；
- 字段 8 航向转换为 `0.01°`；
- 有效状态的 `pos_quality` 当前固定写成 3，并不是模块真实精度等级。

速度滤波使用运动状态滞回：达到约 2 m/s 连续 3 次才进入运动状态，降到约 1 m/s
连续 5 次才退出。低速静止时若坐标突然跳变约 20 m，需要连续确认后才接受，降低静态
漂移对相对位置的影响。

### 6.2 IMU

IMU 帧格式为：

```text
55 55 ID LEN DATA... CHECKSUM
```

校验为从帧头到数据域的 8 位累加和。已实现的帧：

| ID | 内容 | 最小数据长度 |
|---:|---|---:|
| `0x01` | roll、pitch、yaw | 6 |
| `0x03` | ax、ay、az、gx、gy、gz | 12 |
| `0x04` | mx、my、mz、温度 | 8 |

上层目前主要使用 `yaw` 作为低速航向候选、`gz` 判断转弯、`ay < -1500` 判断刹车。
这些阈值使用传感器原始量，不应在不了解量程配置时直接解释为标准物理单位。

### 6.3 通道调度

1. 默认停留 GPS 通道；
2. 收到一条完整 RMC 后切至 IMU；
3. IMU 同时收到姿态帧和六轴帧，或累计收到 6 帧后切回 GPS；
4. 若有语音待播，保存当前通道，临时切到 VOICE；
5. 语音命令结束后恢复此前通道、115200 和接收中断。

默认 `TTL_UART2_SENSOR_LOG_ENABLE=0`，GPS/IMU 解析仍运行，但不持续打印传感器日志，
以减少 USART1 带宽和 CPU 占用。

## 7. BLE 广播协议

### 7.1 无线角色

两个终端都同时执行：

- 发送非连接广播；
- 主动扫描周围广播；
- 从 Manufacturer Specific Data 中识别固定对端。

它不是“一个 Central 连接一个 Peripheral”的业务模型。生成的 GATT 服务仍在工程中，
但当前 V2V 状态交换主链不依赖建立连接或订阅特征值。

扫描参数为间隔 100 ms、窗口 50 ms。广播和扫描响应都带短名称 `MR` 以及状态 Manufacturer
Data。过滤条件为：Company ID `0x1234`、Magic `0x55AA`、协议版本 2、设备 ID
`0x1002`。当前只维护一个 `peerTrack`，不能同时跟踪多个车辆。

### 7.2 Manufacturer Data

```text
Company ID LE: 34 12
Magic LE:      AA 55
State:         16 bytes
```

16 字节状态负载：

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 1 | `proto` | 固定 2 |
| 1 | 2 | `device_id` | 小端，本机默认 `0x1001` |
| 3 | 1 | `msg_counter` | 递增序号，用于过滤重复广播 |
| 4 | 1 | `status_flags` | 运动/转弯/刹车/GPS 等状态位 |
| 5 | 1 | `speed_q` | 速度约为 `speed_cms / 25`，饱和到 255 |
| 6 | 2 | `heading_q` | `0..65535` 映射 `0..360°` |
| 8 | 1 | `yaw_rate_q` | `gz / 32`，有符号饱和量化 |
| 9 | 2 | `lat_low16` | 纬度 `1e-5°` 表示的低 16 位 |
| 11 | 2 | `lon_low16` | 经度 `1e-5°` 表示的低 16 位 |
| 13 | 1 | `pos_quality` | 本地 GNSS 有效时当前为 3 |
| 14 | 1 | `gps_age_q` | 每单位 20 ms，`0xFF` 表示无效 |
| 15 | 1 | `reserved` | 当前本机生成时写 0 |

状态位：

| 位 | 掩码 | 含义 |
|---:|---:|---|
| 0 | `0x01` | moving |
| 1 | `0x02` | turning |
| 2 | `0x04` | braking |
| 3 | `0x08` | GPS valid |
| 4 | `0x10` | high risk |
| 5 | `0x20` | low battery |
| 6 | `0x40` | IMU valid |
| 7 | `0x80` | low confidence |

本机传感器构包当前会设置 moving、turning、braking、GPS valid、IMU valid 和 low
confidence；不会自行设置 high risk 和 low battery。

### 7.3 USART1 外部状态覆盖

USART1 也可接收：

```text
A5 5A TYPE LEN PAYLOAD CHECKSUM
```

校验为 `TYPE XOR LEN XOR 每个 PAYLOAD 字节`。`TYPE=0x01`、长度 16、协议版本 2、
设备 ID `0x1002` 的帧会覆盖本机广播状态，500 ms 内持续有效。

必须注意一个特殊语义：固件从未收到过外部状态时，会从本机 GPS/IMU 构包；但只要
曾经收到过一次合法外部状态，随后超过 500 ms 未更新时不会退回本机传感器，而是清掉
运动、GPS、速度、航向和坐标并置 low confidence。这避免外部源中断后悄悄换数据源，
但也要求外部控制器稳定地以小于 500 ms 的周期供帧。

### 7.4 MP257端工程归属与当前实现状态

如果后续由STM32MP257的M33侧向本终端提供上述外部状态帧，MP257端源码应维护在：

```text

```

对应实现应放在该BSP的`Projects/STM32MP257D-ATK/...`应用工程中，而不是放进本WBA
工程，也不是A35 Linux的`camera_detect`目录。2026-08-10对当前BSP树进行静态检索后，
没有找到`A5 5A`、协议v2的16字节状态、`0x1001/0x1002`或`0x55AA/0x1234`对应的发送
实现。当前能看到的`CM33_OpenAMP_DEMO/OpenAMP_TTY_echo`只是通用OpenAMP/RPMsg回显

因此当前事实是：WBA已经具备“可选接收MP257外部状态帧”的接口，但MP257 BSP中尚未

文档和演示不能把这条可选接口描述成已经完成的MP257联调链路。

## 8. 相对位置和风险判定

### 8.1 数据有效性

- 本机 GPS 最新有效年龄不超过 1500 ms；
- 本机 IMU 数据年龄不超过 1000 ms；
- 对端必须置 GPS valid、质量大于 0、年龄不超过 75×20 ms，并具有非零压缩坐标；
- 对端超过 2000 ms 未收到新序号即超时，清空滤波和语音事件。

### 8.2 航向来源

1. 本机速度至少 2 m/s 时优先采用 GPS course；
2. 低速但 IMU 姿态新鲜时采用校准后的 IMU yaw；
3. 两者都不可用时不能判断方向，只允许走 RSSI 降级提示。

IMU 航向初始安装偏移为 180°。在 GPS 速度足够、IMU 姿态/六轴新鲜且没有明显转弯时，
代码比较 GPS 航向与 IMU yaw；连续 3 次候选差异不超过 15°后建立校准，后续用四分之一
步长缓慢更新偏移。

### 8.3 坐标与距离

对端和本机经纬度都压缩到 `1e-5°` 的低 16 位，通过有符号 16 位差值处理局部回绕；
经度按本机纬度余弦缩放，再按本机航向旋转到：

- `y_front_cm > 0`：对端在本机前方；
- `x_right_cm > 0`：对端在本机右方。

航向来源没有变化时，当前位置与上一位置做 1:1 平均低通。距离使用低成本近似：
`max(|x|,|y|) + min(|x|,|y|)/2`，不是精确平方根。

压缩坐标一步纬度约 1.11 m，普通 GNSS 误差也常大于米级，因此本算法适合趋势实验，
近距离左右方向不能当作高精度真值。

### 8.4 靠近趋势

每个对端最多每 1200 ms 运行一次风险更新：

- 当前距离比上次至少缩短 3 m，连续 2 次才记为 approaching；
- 当前距离比上次至少增加 3 m，一次即记为 receding；
- 变化不足 3 m 时只衰减 closing 计数，不立即切换趋势。

### 8.5 方向选择

目标位于本机后方超过 2 m 时不提示。其余区域只输出四类提示，没有 CENTER 或纯正前方
提示：

- 左侧；
- 右侧；
- 左前；
- 右前。

左右滞回为 ±2 m：保持左侧时需越过右侧 2 m 才改右，保持右侧时需越过左侧 2 m
才改左。前方进入阈值为 7 m，退出阈值为 3 m，以避免边界反复切换。

### 8.6 最终触发条件

有完整位置和航向时，必须同时满足：

1. 方向提示不是 NONE；
2. 对端不是 receding；
3. 对端状态含 moving、turning、braking 中至少一项；
4. 距离不超过 30 m；
5. approaching、high risk、距离不超过 8 m 三者至少满足一项。

GPS 或航向不足时，只有对端在运动、RSSI 有效且不弱于 -75 dBm，才生成一次通用
`GPS_WEAK`/附近来车提示。RSSI 只用于降级粗略提示，不能等价为精确距离。

## 9. 语音事件状态机

### 9.1 曲目映射

| 曲目 | 枚举 | 用途 |
|---:|---|---|
| 1 | `LEFT_RISK` | 左侧来车 |
| 2 | `RIGHT_RISK` | 右侧来车 |
| 3 | `LEFT_FRONT_RISK` | 左前方来车 |
| 4 | `RIGHT_FRONT_RISK` | 右前方来车 |
| 5 | `GPS_WEAK` | 定位不足时的附近来车提示 |

CX-SP5F的`0x07`指定根目录曲目命令为9字节：

```text
FE 09 FF FF 07 SONG_H SONG_L CHECKSUM BE
```

`CHECKSUM` 是前7字节累加和的低8位。但是`0x07`只负责从指定曲目开始播放，播放完后
如何处理由模块当前播放模式决定。如果CX-SP5F处于“全部循环”，单独发送此命令就会
从目标曲目继续播放后续文件并循环，这正是设置曲目6后继续听到7、8等文件的原因。

`v1.8.2`每次启动问候或风险播报都统一发送三帧：

```text
FE 07 FF FF 04 07 BE                 停止当前播放
FE 0A FF FF 18 06 00 00 24 BE       模式6：单曲播放完停止
FE 09 FF FF 07 SONG_H SONG_L SUM BE  指定根目录曲目
```

因此固件不再依赖模块上次掉电保存的播放模式。当前风险逻辑只会主动请求曲目1～5；启用
启动曲目宏后也按同一套一次性流程播放指定曲目。

### 9.2 当前 `v1.8.2` 行为

```text
无风险
  → 同一方向连续满足 1500 ms
  → 成功进入单元素语音队列
  → UART2 切到 VOICE 并播放一次
  → 本次连续风险锁存
  → 风险持续：不再重复播放
  → 风险连续解除 3000 ms：ALERT_REARM，允许下一事件
```

全局两次报告还需至少间隔 3000 ms。对端超时会立即复位事件，不等待解除计时。待播队列
只有一个槽，队列忙时新提示不会覆盖旧提示，也不会打印假的 `ALERT_QUEUE`。

### 9.3 已修复的两类循环播放根因

第一类是应用事件重复入队：旧版只用3秒冷却限制重复频率，播放后候选方向仍然存在，
没有“本事件已经播报”锁存，所以持续风险会每隔约3秒重新入队。

`v1.8.1`已把`bridgeVoiceReportValid`用作连续事件锁存，并增加3秒稳定解除再武装；
同时关闭开机固定播放曲目1，避免复位就产生假的左侧告警。开机曲目宏当前为0。

第二类是CX-SP5F模块内部连续播放：旧版只发`0x07`指定曲目，没有显式设置播放模式。
模块若处于模式1“全部循环”，一次应用事件也会让扬声器从所选曲目开始循环全部文件。
`v1.8.2`在每次选曲前显式停止并设置模式6“单曲播放完停止”，同时修复启动播报和后续
风险播报。两类修复缺一不可。

## 10. 日志与现场判读

USART1 启动日志应包含：

```text
=== V2X Node v1.8.2 (编译日期 编译时间) ===
```

关键业务日志：

| 前缀 | 含义 |
|---|---|
| `WARN:` | 对端状态、方向、距离趋势或降级原因 |
| `ALERT_SRC:` | 最终条件的每一项判定及所选 prompt |
| `ALERT_QUEUE:` | 条件稳定且语音真正成功入队 |
| `[VOICE] play` | 路由器取到提示及其曲目、相对位置 |
| `[VOICE] tx stop:` | 发给CX-SP5F的停止帧 |
| `[VOICE] tx mode-single-stop:` | 设置模式6“单曲播放完停止” |
| `[VOICE] tx select-track:` | 指定根目录曲目 |
| `ALERT_REARM:` | 风险已连续解除，下一事件重新武装 |

诊断时按以下顺序判断：

1. 没有 `WARN`：先查是否收到并匹配 `0x1002` 广播；
2. 有 `WARN`、无 `ALERT_SRC cond_ok=1`：查 GPS、运动位、方向、距离和趋势；
3. 有稳定 `cond_ok=1`、无 `ALERT_QUEUE`：查 1.5 秒稳定时间、事件锁存和队列；
4. 有 `ALERT_QUEUE`、无 `[VOICE] play`：查主循环和路由器；
5. 三条`tx`帧正确、实物语音错误：查CX-SP5F供电、接线和曲目文件；
6. 同一连续风险出现多次 `ALERT_QUEUE`：说明仍发生事件重入或烧录了旧固件。

## 11. 编译、烧录和验证

### 11.1 Keil 编译

1. 在 Windows/Keil 打开 `MDK-ARM/02_test.uvprojx`；
2. 选择 Target `02_test`；
3. 执行 Clean Targets；
4. 执行 Rebuild all target files；
5. 必须确认 `0 Error` 且 HEX 时间戳已更新；
6. 烧录新生成的 `MDK-ARM/02_test.hex`；
7. 复位后确认 USART1 输出 `V2X Node v1.8.2`。

`MDK-ARM/build.log` 留有一次对象文件 `.o.tmp` 重命名权限错误，结果是 `Target not
created`。遇到该问题应关闭占用输出文件的软件、清理 Windows 只读属性并删除/清理
Target 输出后重编译，不能继续烧录旧 HEX。

### 11.2 最小台架验证

1. 分别确认两个终端版本和设备 ID 互补；
2. 查看 GPS 是否有效、IMU 是否持续更新；
3. 确认扫描能匹配对端且消息序号变化；
4. 固定一个风险条件持续超过 10 秒；
5. 期望只出现一次`ALERT_QUEUE`、一次`[VOICE] play`，并且每次播放只有一组
   `stop → mode-single-stop → select-track`；
6. 风险短暂解除不足 3 秒再恢复，不应再次提示；
7. 风险连续解除至少 3 秒，应看到 `ALERT_REARM`；
8. 再次建立风险，才允许第二次语音；
9. 分别覆盖左、右、左前、右前和 GPS 降级提示；
10. 断电/遮蔽对端超过 2 秒，确认旧状态和旧事件被清除。

### 11.3 现场标定建议

- 两端先静止并记录 GPS 漂移，再做运动测试；
- 左右方向测试应拉开数米横向距离，避免落在量化和滞回区；
- 同时保存真实摆放方向、GPS 航向、IMU yaw、`y_front_cm`、`x_right_cm` 和 RSSI；
- 不要只凭语音内容判断算法正确，要对照 `ALERT_SRC`；
- 当前阈值是实验值，未经多场景统计不能宣称完成安全标定。

## 12. 当前限制和维护注意事项

1. 固定本端/对端 ID，只支持一个对端跟踪；
2. 当前仓库只保存端点A的`0x1001→0x1002`配置；端点B需互换两个编译期ID后独立构建，
   同一个HEX不能直接烧到两端；
3. 广播没有认证、加密、重放保护和车辆身份管理；
4. 坐标压缩和普通 GNSS 精度限制了近距离方向可靠性；
5. 相对距离是近似值，风险判断没有完整 TTC、车道模型和地图约束；
6. high risk、low battery 位存在但本机传感器构包不生成；
7. 语音播放会短时阻塞协作式主循环；
8. USART2/PA1/PA2 未完整反映在 `.ioc`，CubeMX 再生成有覆盖风险；
9. 本工程源码、Keil工程和编译所需的ST库已纳入仓库；旧HEX、AXF、对象文件、构建日志
   和Keil用户配置由`firmware/v2v/.gitignore`排除，交付固件必须由源码重新构建；
10. 主机语法检查不能替代 ARMCLANG 完整链接、烧录和双终端实测。

维护时必须同时记录源码版本、Keil 构建结果、HEX SHA256、烧录板编号、设备 ID、曲目表
和实测日志，避免“源码已经修改但板上仍运行旧 HEX”。
