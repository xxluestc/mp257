## 1. 先记住项目主线

### 1.1 一句话介绍

项目基于 STM32MP257 的 Cortex-A35 Linux 和 Cortex-M33，完成骑行风险感知、
跨核事件通信、HUD/骨传导告警、事件行车记录和 BLE 车辆协同预警，并对 Linux
启动和应用运行方式做了优化。

### 1.2 不超过一分钟的介绍

可以这样讲：

> 这是一个基于 STM32MP257 的主动安全骑行辅助系统。A35 运行 Linux，主要负责
> 摄像头采集、NPU 推理、毫米波雷达数据处理、事件录像和网络交互；M33 负责 IMU
> 事件和部分实时任务，两边通过 remoteproc、OpenAMP/RPMsg 配合。业务上实现了
> 摄像头与雷达融合风险检测、BLE-V2V/V2X 协同预警、HUD 和骨传导提示，以及风险
> 事件前后视频保存。我后面还分析了 Linux 启动链路，把 systemd 统计的启动耗时
> 从 103 秒降到 11.84 秒，融合业务就绪从 24.38 秒提前到 12.60 秒。

说完先停，不要马上继续罗列模块。让面试官选择他想追问的方向。

### 1.3 个人工作与项目整体的边界

技术论文中明确写出的个人主要工作是：

- 骨传导语音交互；
- 摄像头与毫米波雷达融合检测；
- 事件触发行车记录；
- BLE-V2X 协同预警。

当前仓库中还包含 A35 Linux 主程序、HUD 软件联动、方向灯、Dashboard、启动优化、
运行维护和 A35 应用 OTA。面试时可以讲自己实际完成和维护过的部分，但要区分：

- “我负责实现”表示自己能说明设计、代码和验证；
- “项目中使用”表示了解接口和数据流，但不一定是自己从零完成；
- HUD 软件收发、显示联动可以讲，不能把整套 HUD 光学设计都说成个人工作；
- BLE-V2V/V2X 是本项目的 BLE 协同通信，不要说成已实现标准 C-V2X 协议栈。

## 3. 系统结构怎么讲

### 3.1 项目中的分工

```text
Cortex-M33
  IMU 采样/事件、部分 BLE-V2X 实时任务
        │
        │ OpenAMP/RPMsg
        ▼
Cortex-A35 Linux
  radar_fusion
    ├── V4L2 摄像头与 NPU
    ├── 毫米波雷达串口
    ├── 融合告警和事件录像
    ├── 骨传导、灯光
    └── UDP → HUD / 手机
```

A35 适合运行 Linux、NPU、视频和网络程序。M33 更适合周期采样、状态判断和对响应
抖动更敏感的任务。这里的重点不是“两个核一定比一个核快”，而是把不同性质的任务
放到合适的运行环境中。

### 3.2 remoteproc、OpenAMP、RPMsg 的关系

- `remoteproc`：Linux 侧管理 M33 固件的加载、启动、停止和状态。
- `OpenAMP`：异构多核通信框架，包含 remoteproc/RPMsg 相关能力。
- `RPMsg`：建立核间消息通道。本项目在 Linux 用户态通过 `/dev/ttyRPMSG0` 收取
  `IMU_ALERT` 和 `V2X_ALERT` 消息。

一句话回答：remoteproc 解决“远端核有没有运行”，RPMsg 解决“两个核运行后怎样
传递业务消息”。`remoteproc0/state=running` 不代表 RPMsg 一定可用。

### 3.3 项目里实际怎么启动 M33

原来 M33 由较晚执行的 `start_dvr.sh` 启动。后来增加 `dvr-m33.service`，在
Linux `sysinit.target` 阶段等待 remoteproc 驱动出现并启动固件。主业务启动时：

- 如果 M33 和 RPMsg 已经正常，直接复用；
- 如果早期服务没有启动成功，保留原来的 Linux remoteproc 回退路径；
- A35 应用重启或 OTA 切换时，默认不停止已经运行的 M33。

实测 M33 `running` 提前到约 3.91 秒。

### 3.4 常见追问

**为什么不让 U-Boot 直接启动 M33？**

当前 U-Boot 虽然有 `rproc` 命令，但 Linux 缺少可靠的 detach/attach 接管证据。
如果 U-Boot 和 Linux 重复加载或重置 M33，可能破坏共享内存和 RPMsg 状态。因此
测试后撤回，改用可验证、可回退的 Linux early service。

**RPMsg 底层是不是共享内存？**

通常基于共享内存中的 vring 传输数据，再由 mailbox/IPCC 一类通知机制提醒对端。
本项目主要使用 Linux 已提供的 RPMsg 字符设备，没有修改 RPMsg 内核驱动，也没有
实现自定义零拷贝通道。

**怎样判断跨核通信真的正常？**

要分别检查 M33 `running`、`/dev/ttyRPMSG0` 出现、A35 能收到业务消息，以及消息
触发后的日志或执行器动作。只看其中一个状态不够。

## 4. 摄像头与毫米波雷达融合

### 4.1 涉及的技术

- V4L2 摄像头采集；
- MJPEG 帧和 JPEG 解码；
- STM32 NPU 推理、SSD MobileNet V2、NMS；
- UART 雷达协议解析；
- 多目标状态、方向滤波和 TTC；
- 连续帧确认和告警状态机。

需要掌握到：能画出一帧摄像头数据和一帧雷达数据分别怎样进入程序，最终在哪个
条件下产生告警。不要求推导完整目标检测网络，也不要把内部识别类别写成项目的核心
产品功能。

### 4.2 当前数据流

摄像头通过 `/dev/video7` 输出 MJPEG。主循环按约 25 FPS 取帧，其中：

- 帧进入 DVR 缓冲；
- 每 10 帧进行一次 NPU 推理；
- NPU 结果经过连续帧确认，减少单帧抖动。

雷达通过 `/dev/ttySTM1` 上报目标。程序解析最多 8 个目标的状态，并维护当前风险
目标。当前融合条件可以简化成：

```text
雷达达到风险条件 + NPU 已确认道路使用者 → 融合告警
```

摄像头不可用时，程序保留纯雷达降级路径。这是可用性设计，但降级模式的误报特性
和融合模式不同，面试时不要说成效果完全相同。

### 4.3 核心功能应该怎样表述

推荐：

> 我负责摄像头/NPU和60GHz毫米波雷达的融合风险检测。雷达提供接近风险，视觉侧
> 用于确认道路使用者，程序通过连续帧状态和告警条件决定是否触发语音、灯光和录像。

不推荐：

> 我实现了车辆识别、精确测速和自动驾驶碰撞算法。

原因是“车辆识别、距离测速”只是内部数据或模型能力，不是当前简历要强调的核心；
项目也没有自动驾驶安全认证和算法精度数据。

### 4.4 为什么要做融合

简短回答：雷达适合提供距离、相对速度和接近趋势，但不擅长确认目标类别；摄像头
可以判断画面中是否存在道路使用者，但距离和全天候稳定性有限。项目没有做复杂的
三维目标级融合，而是把两者的风险状态结合，降低单一传感器直接触发告警的问题。

### 4.5 面试追问

**两个传感器频率不同，怎样处理？**

当前不是严格时间同步的点云/图像联合标定，而是维护各自最近状态，再通过连续帧确认、
超时和告警状态机做决策。回答时要明确这是状态级融合。

**为什么每 10 帧才做一次 NPU？**

摄像头采集和录像需要持续进行，NPU推理不必每帧执行。降低推理频率可以控制计算量，
再用连续状态保持业务稳定。具体频率仍需要根据目标运动速度和告警延迟实测。

**怎么测试融合效果？**

项目记录 `radar_data.csv`、`sensor_events.csv` 和人工标注区间，区分安全接近、危险
接近、不同方向和纯雷达降级。进程运行正常不等于融合效果已经验证，最终仍需要真实
目标进入摄像头和雷达视场。

详细数据流见 [DATA_FLOW.md](DATA_FLOW.md)，现场标定方法见
[RADAR_EXPERIMENT.md](RADAR_EXPERIMENT.md)。

## 5. IMU、BLE-V2X 与告警输出

### 5.1 这部分的逻辑

项目的风险输入不只有摄像头和雷达：

- M33 产生摔倒、急刹和路面颠簸等 IMU 事件；
- BLE-V2V/V2X 提供遮挡路口、弯道等非视距场景的协同信息；
- A35 将风险和导航信息输出到 HUD、骨传导音频、灯光和录像模块。

这样讲比把 IMU、BLE、HUD、音频逐个罗列更有逻辑：前两项是事件来源，后几项是
提示和留证方式。

### 5.2 M33 到手机的事件链

```text
M33 IMU 判断
  → RPMsg
  → A35 radar_fusion
  → 本地 LED / 音频 / DVR
  → UDP 8890
  → HUD
  → UDP 广播 8889
  → 手机 App
```

必须知道验证边界：A35 的 LED 亮只证明本地告警已经触发，不能证明 HUD 收到、手机
收到或短信最终发送。当前协议没有手机收包和短信成功回执。

### 5.3 BLE 方向灯链路

```text
MP257 A35 UART
  → CH9140 BLE 透明串口（Peripheral）
  → STM32WBA（Central）
  → 左右方向灯 GPIO
```

MP257 发送 `RISK LEFT/RIGHT/CENTER/CLEAR`，WBA 控制灯并回复 ACK。手机不在这条
控制链路中。BLE 断开时 WBA 清灯，避免保留过期风险状态。

WBA端的完整固件位于
[`E04-2G4M10S1AX`](../../../../E04-2G4M10S1AX/README.md)，不是只有MP257侧
几条串口命令。需要掌握的实际过程是：

1. CH9140保持BLE Peripheral，广播名称`CH9140BLE2U`和FFF0服务；
2. STM32WBA54作为Central扫描，按名称或FFF0匹配目标；
3. 建立GAP连接后，依次发现FFF0服务、FFF1 Notify、FFF2 Write和FFF1的CCCD；
4. 写CCCD使能Notify后才进入`GATT=ready`；
5. MP257的UART数据经FFF1通知到WBA，WBA解析`RISK`命令并控制PA7/PA5；
6. WBA通过FFF2回写`ACK`，再由CH9140串口返回MP257；
7. 断线、复位或GATT失败时清灯并重新扫描。

WBA固件采用STM32 HAL、CMSIS、STM32_WPAN协议栈和`UTIL_SEQ`协作式调度。UART侧使用
Receive-to-Idle DMA和512字节环形队列，BLE数据按20字节分块。核心源码是
`app_ble.c`、`ch9140_client.c`和`ble_uart_bridge.c`。

这里要主动说明：当前E04工程已经移除旧GNSS、IMU、语音和V2X业务，它实现的是V2V
功能中的BLE接入、风险状态传递和方向灯执行，不是独立完整的V2V系统或标准C-V2X
协议栈。

面试可简要表述：

> V2V部分使用CH9140和STM32WBA54建立BLE链路。WBA作为Central完成扫描、GATT服务
> 发现和Notify订阅，接收MP257发来的方向风险命令控制左右告警灯，并通过反向特征值
> 返回ACK；断线时自动清灯并重新扫描。

可能追问：

- 为什么WBA必须是Central？
- GAP连接成功为什么还不能直接传业务数据？
- FFF1、FFF2和CCCD分别做什么？
- BLE一次只发送20字节时，长数据怎样处理？
- 为什么UART DMA回调只写环形队列，不直接调用GATT API？
- 断线后为什么必须清除方向灯？
- 当前链路为什么不能称为安全的标准V2V协议？

#### 5.3.1 独立双WBA广播语音原型

另有`V2V_keil/E04-2G4M10S1AX`独立原型，不能和上述CH9140方向灯固件混为一谈。
它让两个WBA终端同时广播和扫描Manufacturer Data，不建立业务GATT连接。每个广播携带
16字节状态，包括设备ID、速度、航向、yaw rate、压缩经纬度、定位质量和状态位；接收端
把对端位置投影到本机前-右坐标系，根据距离趋势、运动状态和方向选择左/右/左前/右前
语音，再通过USART2外部多路选择板驱动MP3模块。

可以用下面这段回答“你做的V2V算法是什么”：

> 双终端原型基于BLE非连接广播交换轻量状态。接收端先检查GPS和IMU新鲜度，运动时优先
> 使用GPS航向，低速时使用经GPS校准的IMU yaw；随后把坐标差旋转到车体坐标系，做简单
> 低通和距离趋势判断。风险需要对端运动、30米内、不是远离，并满足靠近、高风险位或8米
> 内之一；方向稳定1.5秒后只提示一次，风险稳定解除3秒才重新武装。

这个原型值得主动说明三个工程判断：

1. 16位低位经纬度采用`1e-5°`量化，近距离方向受米级GNSS误差影响，当前是实验验证而非
   量产安全算法；
2. 固件只过滤固定对端`0x1002`并维护一个`peerTrack`，还不支持多车目标管理；
3. 广播没有身份认证、加密和重放保护，不能称为标准或安全的C-V2X实现。

还要知道两端不能烧同一个默认HEX：当前源码是A端`0x1001→0x1002`，B端必须把本端和
期望对端ID互换后单独构建，否则双方都会广播`0x1001`并过滤掉彼此。

循环语音问题是一个适合面试的问题排查故事，而且最终确认有两层根因：应用层把3秒冷却
当成事件去重，风险持续时仍会周期性重新入队；设备层只向CX-SP5F发送指定曲目命令，
模块若保留“全部循环”模式，就会继续播放后续文件。应用层改为候选稳定、已播锁存、
稳定解除再武装；设备层每次按“停止→模式6单曲播放完停止→指定曲目”完成一次事务。
这个修复说明“限频”和“事件生命周期”不同，同时驱动不能依赖外设上一次掉电保存的状态。

### 5.4 HUD 和骨传导

## 6. 事件触发行车记录

### 6.1 涉及的技术

- V4L2 摄像头输出 MJPEG；
- 触发前预缓存和触发后继续采集；
- GStreamer 流水线；
- JPEG 解码、V4L2 H.264 编码、MP4 封装；
- 子进程编码和进程回收；
- TF 卡文件存储。

简历不需要全部写出。简历只保留“GStreamer、H.264事件录像、保存事件前后视频”
即可。上面的细节用于面试追问。

### 6.2 三个容易混淆的概念

- MJPEG：摄像头输出格式，每帧是一张独立 JPEG 图像。
- H.264：视频编码格式，利用帧间压缩降低文件体积。
- MP4：容器格式，用来封装编码后的视频流。

GStreamer 是搭建媒体处理流水线的框架，不是编码格式。当前主要流水线是：

```text
JPEG 帧序列
  → jpegdec
  → videoconvert / NV12
  → v4l2slh264enc
  → h264parse
  → mp4mux
  → MP4 文件
```

### 6.3 项目中如何保留触发前视频

如果只在告警发生后开始录像，就没有事故发生前的过程。因此程序在发现可能目标后
开始保存 MJPEG 帧，维护最近一段时间的帧索引。风险确认后继续记录触发后的帧，最后
异步编码成 MP4。当前目标是保存事件前后各 15 秒。

编码放在子进程中，主循环只负责回收结果，避免编码阶段长时间阻塞雷达、摄像头和
告警处理。

### 6.4 当前实现的限制

当前帧索引有上限，板载ext4上的原始MJPEG缓存文件会持续append，但录像窗口已限制
为“第一次触发前15秒到最后一次触发后15秒”，连续事件最长60秒。异常断电仍可能
损坏正在写入的临时缓冲，正式MP4则在双重验证后原子提交。后续更合理的方式是：

- 在 RAM 中建立按时间和总字节双重限制的 MJPEG 环形队列；
- 触发后冻结前置帧，并把后置帧流式写入；
- 先写 `.partial`，完成后 `fsync` 再原子改名；
- 内存不足时缩短预缓存，不能让系统 OOM。

这部分是已确认的改进方向，不要说成已经完成。详见
[RUNTIME_STORAGE.md](RUNTIME_STORAGE.md)。

### 6.5 常见追问

**为什么不一直写完整 MP4？**

事件录像关注的是风险前后过程。一直录像会增加存储占用和写放大，预缓存可以在
保留事前画面的同时控制最终视频数量。当前临时缓存写板载ext4，正式录像最多12段
或2GiB；以后仍可改为有界RAM环形缓存进一步减少存储写入。

**为什么使用 MJPEG 做预缓存？**

摄像头本身输出 MJPEG，保存压缩帧比缓存 RGB 占用更小，也不需要在主循环中重新
编码每一帧。缺点是压缩率通常不如 H.264，最终仍要转码封装。

**为什么用子进程，不直接在线程里调用编码库？**

现有方案通过成熟命令行流水线快速集成，并把编码故障与主业务进程隔离。代价是需要
管理子进程和临时文件；如果追求更低开销，可以后续改成 GStreamer API 长生命周期
pipeline，但实现复杂度更高。

## 7. Linux 启动优化

这是简历中最适合重点展开的一部分，因为有完整的基线、定位过程、改动、数据和回退。

### 7.1 涉及的技术

- BootROM、TF-A、OP-TEE、U-Boot、Linux kernel、userspace 启动阶段；
- systemd unit、target、依赖和关键链；
- journal 单调时间、`CLOCK_BOOTTIME`；
- udev 设备枚举和具体设备等待；
- remoteproc/RPMsg；
- shell 启动脚本；
- 串口协议 ACK 和超时机制。

至少要掌握到：能解释每个指标的起点和终点，能说明为什么两个 90 秒服务不会相加成
180 秒，能指出优化前后的主要瓶颈。

### 7.2 指标定义

- `systemd 总启动 11.84 s`：Linux 内核入口到 systemd 启动完成。
- `Fusion core ready 12.60 s`：Linux 内核入口到融合主业务完成初始化。
- 两者不是串行相加；业务服务与其他 systemd 服务并行启动。
- 这两个数字都不包含 BootROM、TF-A、OP-TEE 和 U-Boot。

简历中不要写成“上电到业务可用 11.84 秒”。更准确的写法是“systemd 启动耗时”
或“Linux 启动耗时（不含 bootloader）”。

### 7.3 优化前的主要问题

```text
kernel:             2.212 s
userspace:        100.792 s
systemd total:    103.005 s
Fusion ready:      24.38 s
```

主要耗时：

- `snmpd.service` 和 `snmptrapd.service` 分别等待约 90 秒后失败；两者并行，所以
  关键路径增加约 90 秒，不是 180 秒；
- TF 卡 fsck 曾耗时 20.7 秒，原因包含 FAT 损坏，不能简单禁用；
- M33 由较晚的业务脚本启动；
- 启动脚本串行启动 HUD、Dashboard并包含固定等待；
- 雷达四条命令即使已收到回复，仍各等待完整 1 秒超时；
- 业务依赖全局 `udev-settle` 和 `network-online`，等待范围过大。

### 7.4 实际优化步骤

1. 用 systemd 时间、关键链和单调日志建立统一时间线，先确认真正的启动路径。
2. 审计并停用项目不使用且启动失败的 SNMP 服务，保留可回退记录。
3. 将 M33 移到 Linux sysinit 阶段启动，主业务保留失败回退。
4. 修复 TF 卡并保留 fsck，不用牺牲数据安全换启动数字。
5. 雷达收到完整且命令匹配的 ACK 后提前结束等待，同时保留原超时和稳定间隔。
6. 减少启动脚本重复命令、重复清理和固定 sleep。
7. 用摄像头、雷达串口、GPIO 等具体设备等待替代全局 udev settle。
8. 让 dnsmasq 只等待产品的 hostapd，不再等待全局 network-online。
9. OTA 没有待恢复事务时走轻量检查，不加载完整 Python 安装器。
10. 连续冷启动三次，并检查 M33、RPMsg、雷达 ACK、摄像头/NPU、HUD、网络和 TF。

### 7.5 有说服力的中间数据

| 项目 | 优化前 | 优化后 |
|---|---:|---:|
| systemd 总启动 | 103.005 s | 中位数 11.841 s |
| M33 running | 约 11.7～17 s | 中位数 3.908 s |
| Fusion core ready | 24.38 s | 中位数 12.602 s |
| 雷达初始化 | 4.923 s | 0.930 s |
| 主程序入口到 Fusion ready | 5.326 s | 1.341 s |
| 启动脚本到主程序入口 | 2.010 s | 约 0.131 s |

最后三次冷启动的 Fusion ready 范围为 12.386～12.638 秒，不能只报最好的一次。

### 7.6 为什么现在还需要约 12.6 秒

当前已经没有 90 秒级异常等待。剩余时间主要是实际设备和功能准备：

- Linux 内核约 2.06 秒；
- M33 在约 3.91 秒运行，不是当前瓶颈；
- V4L2 摄像头节点约在8.50～9.20秒完成udev初始化，是最晚业务设备之一；
  2026-08-09实机已确认`/dev/video7`为USB UVC摄像头。硬件约1.29秒已被USB发现，
  延后主要来自udev冷插拔与媒体模块按需加载，而且本次节点早于`dvr.service`，
  没有实际阻塞业务；
- TF 卡 fsck 约 1.3～1.8 秒属于历史测量；当前录像使用板载ext4，不再依赖它；
- Wi-Fi AP 和 DHCP 是当前 systemd 关键链中的必要功能；
- 主程序入口到融合就绪约 1.34 秒，其中雷达初始化约 0.93 秒；
- RPMsg 线程还保留固定 1 秒等待，所以 ready 消息约在 13.60 秒发出。

这些项目有不少并行执行，不能把每一项耗时直接相加。

### 7.7 为什么没有继续改 bootloader 和内核

当前 `systemd-analyze` 看不到 bootloader。已知 extlinux 菜单约有 2 秒等待，
initramfs 解包约 0.42 秒，但没有 UART、可靠备用启动项和完整板旁回归时，直接改
生产启动配置可能同时失去 Linux 和 SSH 恢复入口。

内核阶段约 2 秒，不是第一大瓶颈。项目依赖摄像头媒体拓扑、NPU reserved-memory、
Wi-Fi、音频和 remoteproc，盲目裁剪内核或设备树风险大、收益不明确。因此先完成
userspace 高收益优化。

### 7.8 两分钟讲述模板

> 我先定义了两个指标：Linux systemd 启动完成和融合业务 ready，并使用单调时间
> 避免 RTC 校时影响。基线里内核只有约 2.2 秒，userspace 却超过 100 秒。沿关键
> 依赖和日志查到两个项目不用的 SNMP 服务并行超时约 90 秒，所以总耗时不是两个
> 服务简单相加。之后我把 M33 移到 Linux sysinit 阶段启动，保留业务脚本回退；
> 雷达初始化从固定等待改为收到匹配 ACK 后结束，但保留原超时；再把全局 udev 和
> 网络等待收窄到具体设备和 Wi-Fi AP。最终连续三次冷启动的 systemd 中位数是
> 11.84 秒，融合业务 ready 是 12.60 秒。没有继续修改 U-Boot 和内核，因为当前
> 缺少可靠恢复和完整现场回归，收益也不是当前最大的。

详细证据和命令见 [BOOT_OPTIMIZATION.md](BOOT_OPTIMIZATION.md)。

## 8. systemd 服务、运行维护和 OTA

这部分在简历中只占一行，不要把它写成很多故障列表。面试官追问“长期运行怎样保证”
时再展开。

### 8.1 服务管理需要掌握什么

- `Type=simple` 与 `Type=oneshot` 的区别；
- `Restart=on-failure` 何时触发；
- 父脚本、业务子进程和日志管道的生命周期；
- SIGTERM、SIGKILL、`wait` 和僵尸/残留进程；
- 服务 active、进程存在、业务数据新鲜是不同层次的健康状态。

项目中：

- `dvr-m33.service` 是一次性初始化动作，使用 `Type=oneshot`；
- `dvr.service` 运行主业务，使用 `Type=simple` 和 `Restart=on-failure`；
- Dashboard 已拆成独立服务，不随融合主程序一起退出；
- `dvr.service=active` 还不够，需要确认 `radar_fusion` 进程和 Dashboard
  `stale=false`。

### 8.2 日志和存储

- 普通文本日志按容量轮转；
- 正在被进程打开的日志采用 copy-truncate，保持原文件描述符可继续写；
- CSV 在写入进程内部执行 `fflush → fclose → rename → reopen`，避免外部截断与
  写线程竞争；
- `radar_state.json` 通过临时文件和 rename 更新；
- MP4 是业务数据，当前不按普通日志自动删除。

面试时不用背每个文件的容量，能解释为什么文本日志、CSV 和事故视频不能使用同一
清理策略即可。

### 8.3 OTA 做了什么

OTA 只更新 A35 Linux 应用，不更新 M33、U-Boot、内核、设备树和 rootfs。

```text
上传包
  → SHA-256/清单校验
  → 安全解压到 staging
  → 停止 dvr.service
  → 原子切换当前 release 符号链接
  → 启动服务
  → 健康检查
  → 成功保留新版本，失败切回上一版本
```

安装进程独立于 HTTP 请求，手机断开后已开始的安装不会跟着请求结束。板子下次启动
会检查未完成事务并优先恢复稳定版本。

### 8.4 OTA 必须主动说明的边界

- SHA-256 只能检查传输完整性，不能证明包由可信发布者生成；
- 当前使用私有 Wi-Fi 内的 HTTP，不是面向公网的量产安全方案；
- 量产还需要包签名、公钥验签、认证、重放/降级保护和 HTTPS；
- 当前只对 A35 应用做版本切换，不能称为整机 A/B 系统升级。

详细实现见 [OTA.md](OTA.md) 和 [RUNTIME_STORAGE.md](RUNTIME_STORAGE.md)。

- 处理：确认项目无依赖后停用，并保存原状态和回退方式。
- 验证：冷启动并检查核心服务、设备和业务状态。
- 重点：并行服务耗时不能相加，必须找关键路径。

### 11.2 雷达初始化接近5秒

- 现象：四条配置命令都有回复，但初始化仍接近5秒。
- 定位：代码收到回复后仍等待每条命令完整1秒超时。
- 处理：解析完整回复帧，只有命令字匹配时提前结束；异步上报帧跳过；原超时保留。
- 结果：4.923秒降到0.930秒。
- 重点：不是删除超时，而是用协议ACK替代无条件等待。

### 11.3 U-Boot启动M33的方案被撤回

- 目标：进一步提前M33运行时间。
- 验证：U-Boot具备rproc命令，但Linux仍重新启动M33，内核还报告缺少detach mailbox。
- 决策：无法证明生命周期能安全接管，撤回生产测试文件。
- 替代：在Linux sysinit阶段启动M33，并保留主业务回退。
- 重点：拒绝一个高风险方案也属于工程判断，不要只讲“我改了什么”。

### 11.4 服务显示运行但核心业务退出

- 现象：`dvr.service`仍是active，Dashboard还可访问，但融合状态不再更新。
- 原因：真正的`radar_fusion`退出后，父脚本卡在日志子进程回收，systemd看见的主脚本
  没有退出，因此不会触发Restart。
- 处理：按父PID清理日志子进程，有界等待，主脚本返回非零，让systemd重新拉起。
- 验证：SIGKILL主进程后，`NRestarts`增加，新的业务PID出现，Dashboard恢复新鲜。
- 重点：进程活着、unit active和业务健康不是同一个概念。

### 11.5 TF卡检查与业务挂载冲突

- 现象：TF卡fsck耗时长，并出现缓存目录损坏。
- 风险：业务手工挂载和fsck可能并发操作FAT。
- 处理：先备份正式数据，离线修复，再修正启动脚本的等待逻辑，保留fsck。
- 重点：启动优化不能以关闭数据保护为代价。
