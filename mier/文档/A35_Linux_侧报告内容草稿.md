**（3）摄像头主导的雷达-视觉融合盲区检测**

系统采用"摄像头先发现、雷达后裁决"的融合策略。A35 核心运行 SSD MobileNet V2 神经网络，对 USB 摄像头采集的 1280×720 视频流进行实时目标检测，识别骑行场景中的行人、自行车、汽车、摩托车等道路用户；当 NPU 连续两帧确认存在道路用户后，启动视频缓冲。同时，A35 通过 USART1 接收 60 GHz 毫米波雷达数据，解算目标距离、径向速度与碰撞时间 TTC。只有当雷达判断存在真实碰撞风险（TTC 低于阈值）且 NPU 已确认目标为道路用户时，系统才触发 LED 告警、骨传导语音提示与行车记录保存。该机制有效抑制了单一传感器误报，提高了城市复杂环境下的告警可靠性。

**（6）双核协同的视频锁存与多事件触发**

系统充分利用 STM32MP257 的异构双核架构：M33 实时核负责 IMU 姿态解算、摔倒/急刹识别与 V2X 协同告警，A35 Linux 核负责摄像头采集、NPU 推理与 DVR 行车记录。两核通过 OpenAMP/RPMsg 通道交互，A35 接收 M33 发送的摔倒、急刹、V2X 危险等事件，将其作为行车记录保存的补充触发源，同时驱动骨传导音频告警。骨传导与 LED 告警由 A35 本地直接控制，确保告警响应延迟最低。双核协作实现了实时性要求高的感知任务与计算密集型的 AI/视频任务的分层处理。

### 2.1 整体介绍（A35 侧补充）

**Word 插入位置**：在 2.1 节现有系统整体介绍之后，补充 A35 Linux 核的数据流与模块分工。

系统硬件上以 STM32MP257 异构双核 SoC 为核心。M33 实时核运行裸机/RTOS 程序，负责低延迟的传感器采集与 V2X 通信；A35 Linux 核运行 Linux 系统，负责计算密集型的摄像头采集、NPU 推理与 DVR 视频编码。两核通过 OpenAMP 框架下的 RPMsg 通道实现通信，A35 作为 RPMsg 服务端监听 M33 发送的事件，M33 作为客户端在检测到摔倒、急刹或接收到 V2X 危险告警时主动向 A35 发送消息。

A35 Linux 侧软件自下而上可分为四层：

- **设备层**：USB 摄像头、USART1 毫米波雷达、GPIO 子系统、ALSA 音频子系统、RPMsg 字符设备。
- **驱动/采集层**：V4L2 视频采集模块负责以 25 fps 读取 MJPEG 帧；雷达串口解析模块负责按帧协议解包目标信息并计算 TTC；RPMsg 接收模块负责解析 M33 事件。
- **算法/决策层**：NPU 推理模块调用 `libstai_mpu` 运行 SSD MobileNet V2 模型，输出目标类别、置信度与边界框；融合决策模块维护目标存在、确认、否认等状态，综合雷达告警结果产生最终触发信号。
- **应用/输出层**：DVR 模块管理视频缓冲、保存与异步编码；LED 控制模块通过独立线程实现告警闪烁；音频提示模块接收告警事件并播放预置提示音。

### 2.3.1 软件整体介绍（A35 Linux 端）

**Word 插入位置**：在 2.3.1 节（目前为模板占位）单独成节，标题建议为"2.3.1 软件整体介绍"下的"（1）A35 Linux 端软件整体架构"。

**建议字数**：800-1000 字。

**是否需要配图**：是，需插入"图 2-X A35 端主程序数据流图"。

A35 Linux 端主程序 `radar_fusion` 是一个单进程多线程应用，核心流程围绕摄像头帧采集展开。主循环以阻塞方式从 V4L2 缓冲区读取 MJPEG 帧，每采集一帧完成三项任务：更新 DVR 帧缓冲、周期性触发 NPU 推理、以及接收并处理雷达数据。

**主循环时序**如下：

1. **帧采集**：从摄像头获取一帧 MJPEG 图像，时间戳以程序启动时刻为基准。
2. **DVR 缓冲写入**：若当前处于录制状态，将 JPEG 数据追加到原始帧文件，并在索引文件中记录该帧的大小与文件偏移。
3. **NPU 推理**：每采集 5 帧触发一次 NPU 推理。将 MJPEG 解码为 YUV 后缩放为 640×480 RGB，送入 SSD MobileNet V2 模型。推理结果经过道路用户过滤，仅保留人、自行车、汽车、摩托车、公交车、卡车六类目标。
4. **雷达数据接收**：非阻塞读取串口，当收到完整一帧雷达数据时，更新目标列表并计算是否触发告警。
5. **融合决策**：若 NPU 已确认目标且雷达告警，触发 DVR 保存、LED 闪烁与骨传导提示。
6. **RPMsg 事件处理**：检查 M33 发送的摔倒/急刹/V2X 事件，将其作为行车记录保存的补充触发源。

**多线程设计**如下：

**[表 2-1 A35 端线程/进程划分]**

| 线程/进程 | 职责 | 触发方式 |
|----------|------|---------|
| 主线程 | 摄像头采集、NPU 调用、雷达读取、融合决策 | 主循环 |
| DVR 编码子进程 | ffmpeg 编码 MP4 | 子进程，触发后异步执行 |
| LED 闪烁线程 | PD11 GPIO 电平翻转 | 告警时启动 |

#### （3）毫米波雷达数据解析模块

A35 通过 USART1 与 60 GHz 毫米波雷达通信，波特率设置为 921600 bps。雷达按固定协议周期上报检测到的目标信息，包括目标 ID、距离、角度、径向速度等。解析模块维护一个目标列表，计算每个目标的碰撞时间 TTC，并根据最近目标距离与 TTC 综合判断是否触发告警。TTC 计算逻辑为距离除以相对靠近速度，同时结合最小距离进行综合判断。当雷达检测到目标且满足告警条件时，告警标志置 1；当目标消失超过 3 秒时，系统判定目标消失，清零活跃状态。

#### （4）雷达-视觉融合决策模块

融合决策是 A35 端的核心逻辑。该模块同时接收 NPU 的道路用户检测结果与雷达的碰撞风险结果，通过状态机判断是否存在真实危险。设计要点如下：

- **NPU 状态机**：
  - 当前是否检测到道路用户；
  - 连续 2 帧检测到道路用户后确认真实目标；
  - 连续 3 帧未检测到道路用户后判定雷达可能误触发；
  - 新目标出现时，自动重置否认与确认状态，打破死锁。

- **触发条件**：
  - 缓冲启动：摄像头检测到道路用户；
  - 保存触发：雷达告警且 NPU 已确认、未被否认；
  - LED 与音频：雷达告警且 NPU 已确认、未被否认。

#### （5）DVR 行车记录模块

DVR 模块负责视频缓冲、触发保存与异步编码。其工作流程为：

1. **缓冲启动**：NPU 检测到道路用户后，创建缓冲目录，打开原始帧文件与索引文件，开始循环写入 JPEG 帧。
2. **循环缓冲**：每帧 JPEG 按"长度 + 数据"的格式追加到原始帧文件，索引文件记录每帧的时间戳、文件偏移与长度。
3. **触发保存**：当融合决策判定需要保存时，记录触发时刻，继续采集 15 秒。
4. **异步编码**：触发后创建子进程，从缓冲文件中提取所需帧，生成文件列表，调用 ffmpeg 编码为 MP4。编码过程在子进程中完成，不影响主循环继续采集与检测。
5. **状态重置**：编码完成后，清理缓冲文件，重置 NPU 与 DVR 状态，等待下一次触发。

**[表 2-2 DVR 模块关键文件说明]**

| 文件 | 作用 |
|------|------|
| 原始帧文件 | 存储原始 MJPEG 帧数据 |
| 索引文件 | 存储每帧的时间戳、偏移、长度 |
| 文件列表 | ffmpeg 拼接输入列表 |
| 紧急视频文件 | 最终保存的 MP4 视频 |

#### （6）LED 告警控制模块

LED 控制通过 Linux GPIO 字符设备实现，控制引脚为 PD11。程序请求该 GPIO 线并配置为输出模式。告警时启动一个独立线程，以 200 ms 周期翻转电平，实现闪烁效果；告警解除后，线程退出并熄灭 LED。

---

#### （7）骨传导音频提示模块

骨传导扬声器由 A35 通过 ALSA 音频子系统驱动，采用 I2S 接口的音频解码芯片。系统为不同危险场景配置了不同的预置提示音，使骑行者无需查看 HUD 即可通过声音判断告警来源与类型：

- **后方碰撞风险**：播放"注意后方来车"；
- **摔倒事件**：播放"检测到摔倒"；
- **急刹事件**：播放"前方急刹"；
- **V2X 协同危险**：播放"路口来车"或"前方危险"。

音频提示与 LED 告警同步触发，为骑行者提供"声光双通道"提示。骨传导方式保持耳道开放，骑行者仍可感知环境声与汽车鸣笛，兼顾安全性与信息可达性。

#### （8）RPMsg 双核通信模块

### 2.2.3 电路各模块介绍（A35 相关接口补充）

**Word 插入位置**：在 2.2.3 节队友已写的 V2X PCB 内容之后，新增"A35 Linux 侧接口电路"小节。

**建议字数**：400-600 字。

**是否需要配图**：是，需插入"图 2-X A35 侧外设接口连接图"。

A35 Linux 侧通过以下硬件接口连接摄像头、雷达、LED、音频与 TF 卡：

**USB 摄像头接口**

USB 摄像头直接接入开发板 USB 2.0 Host 接口，由 Linux V4L2 子系统驱动。摄像头输出 MJPEG 格式视频，分辨率 1280×720，帧率 25 fps。

**毫米波雷达接口**

雷达模块通过 TTL 串口与 STM32MP257 的 USART1 连接。USART1 引脚为 PG14（TX）与 PG15（RX），波特率 921600 bps，数据位 8、停止位 1、无校验。

**LED 告警接口**

告警 LED 连接至 GPIO PD11。程序通过 GPIO 字符设备控制该引脚，配置为推挽输出，周期翻转实现闪烁。

**骨传导音频接口**

骨传导扬声器由 I2S 音频解码芯片驱动。解码芯片通过 I2S 接口接收 A35 音频数据，经功放输出至骨传导振子。模式控制引脚由 GPIO 控制。

**TF 卡存储接口**

DVR 视频文件保存至 SDMMC 接口连接的 TF 卡，挂载点为 `/run/media/mmcblk0p1/`，DVR 数据存储在该目录下的 `dvr/` 子目录中。

**[表 2-4 A35 Linux 侧硬件接口汇总]**

| 外设 | 接口类型 | 设备节点 | 关键引脚 |
|------|---------|---------|---------|
| USB 摄像头 | USB 2.0 Host | 视频设备节点 | USB 数据差分线 |
| 毫米波雷达 | USART1 | 串口设备节点 | PG14 / PG15 |
| LED 告警 | GPIO | GPIO 字符设备 | PD11 |
| 骨传导音频 | I2S + GPIO | ALSA 默认设备 | I2S 时钟/数据/片选 + 模式控制 |
| TF 卡 | SDMMC | TF 卡挂载点 | SDMMC 数据/时钟线 |
| M33 通信 | OpenAMP/RPMsg | RPMsg 字符设备 | 共享内存通道 |
